## 3. 关键改造一：Embedding 上云（DashScope）

### 3.1 选型

- 模型：`text-embedding-v4`，维度取 **1024**（v4 支持 2048/1536/1024/768/512/256/128/64；1024 与现有 schema 一致，检索质量与成本平衡）。
- 接口：OpenAI 兼容模式 `https://dashscope.aliyuncs.com/compatible-mode/v1/embeddings`（广州访问国内域名，延迟约 20–50ms）。
- 调用约束（以实现时官方文档为准）：
  - 单次请求最多 **10 条文本**；
  - 单条文本上限 8192 token；
  - 有 RPM/TPM 限额，需要重试与并发上限。
- **必须全量重建索引**：哈希/ONNX/BGE 向量空间与新模型不兼容；即使维度同为 1024 也不能混用。

### 3.2 新增模块 `common/embedding.py`

职责：唯一的 embedding 出口（业务代码不直接调 SDK）。

```python
class CloudEmbedder:
    def encode(self, texts: list[str]) -> list[list[float]]: ...   # 自动分批(≤10)+重试+LRU
    def encode_one(self, text: str) -> list[float]: ...
    def health(self) -> tuple[bool, str]: ...                       # 带 TTL 的小样本探针

def get_embedder() -> CloudEmbedder: ...                            # 进程级单例
```

实现要点：

| 项 | 做法 |
|---|---|
| 分批 | `batch_size=10`（env 可调，硬上限 10） |
| 重试 | 指数退避 3 次，仅对 429/5xx/超时；4xx 立即失败 |
| 超时 | 单请求 15s；整体索引任务按批累计日志 |
| 缓存 | 查询侧 LRU（默认 2048 条），键为模型名+文本 hash；索引侧不缓存 |
| 失败语义 | **fail-closed**：索引任务失败→报错退出；查询失败→上层返回 `degraded`，不编造结果 |
| 可靠性 | 连续失败 5 次熔断 30s，健康检查显示 `down` |

### 3.4 迁移步骤

1. 备份旧 `data/chroma`（384 维，不可复用）。
2. 设置新 collection 名（代码已改），删除旧目录内容后重建。
3. 运行一次性重建脚本：`python -m scripts.rebuild_index --source all`。
4. 记录输出：条数、token 估算、耗时、失败项。
5. 校验：`/api/v2/health` 的 `embedding` 与 `vector` 均为 `ok`；`/api/v2/kbqa/meta` 的 `count` 与语料一致。

## 4. 关键改造二：去掉 Reranker

### 4.1 现状判断

- KBQA 链路（`search_kb`）目前依赖 BGE-Reranker 提升 top-k 精度；
- 案例域**本来就是确定性重排**（状态权重 × 新鲜度 × 有效性），并没有用神经网络重排；
- 因此「去 reranker」的实际工作只有两处：`rag_tools` 删代码、案例域调候选数与阈值。

### 4.2 替代策略（不引入任何本地模型）

| 环节 | 替代做法 |
|---|---|
| 召回 | 候选数从 12 提到 **18–24**（`n_results` 的 4–6 倍），保证答案在候选池里 |
| 精排 | 复用现有确定性重排：`status_weight × freshness × verified` + 受控术语命中加成 |
| 拒答 | 用 **cosine 相似度绝对值 + 术语闸门**；重新标定 `case_policy.yaml` 三个阈值 |
| KBQA | 增加可选 `KBQA_MIN_SCORE`（默认关闭），低于阈值走「检索不到」而不是让 LLM 自由发挥 |

### 4.3 必做：阈值重标定

`case_policy.yaml` 明确写了「换真实 embedding 后必须重跑标定」，且当前值（0.18/0.20/0.27）是按哈希分数定的。云端 embedding 的无关问句相似度通常在 0.3–0.5，**直接沿用的结果是「什么都答」**。

做法：

1. 用 `data/case_seed.json` + 20 条无关问题（食堂、天气、股票…）构造标定集；
2. 跑现有 `tools/calibrate_answer_thresholds.py`（或按其逻辑改为调用新 embedder）；
3. 取「无关组 p95」与「相关组最低分」之间的间隔，设置 `answer_min_score` / `low_confidence_threshold` / `answer_score_without_terms`；
4. 把新值与语料规模一起写回 YAML 注释，避免下次又被当成恒定真理。

**标定在哪跑**：不必在服务器上跑。标定只依赖「同一个 embedding 模型 + 同一份案例语料」，与部署位置无关。推荐本地（开发机）跑：

- 条件：`EMBEDDING_MODEL=text-embedding-v4`、`EMBEDDING_DIM=1024` 与生产完全一致；使用 `data/case_seed.json` 同一份语料；配同一个 DashScope key。
- 产出：三个阈值写回 `case_policy.yaml`，随代码部署到广州即可。
- 不建议用 `CASE_VECTOR_BACKEND=memory` 做标定——哈希分数的分布与云端 cosine 完全不同，标出来的值没有意义；标定必须走云端 embedding + cosine。
- 服务器上只在验收阶段复跑一次「抽样对照」（10 条问题看分数区间），确认部署环境与本地一致即可。

### 4.4 制度库（KBQA）排序方案（同样去 Reranker）

制度问答的检索链路比案例域更依赖 reranker，因为语料是 16 个部门、内容高度相似的制度条文。去掉 reranker 后**不能只靠单一 dense 相似度**，建议按下面四层排：

**① 先分级，别让所有问题都进向量检索**（现有架构已具备，保持不变）

```
L0 缓存 → L1 FAQ 精确匹配（纯词面，无 embedding）
        → L1.5 域内意图（kbqa_intent 词表，sub-ms）
        → L2 向量检索（只处理长尾）
```

大量高频问题在 L1 就被拦掉，L2 只承担长尾——这本身就把对精排的依赖降了一半。

**② L2 用「dense + 本地 BM25」两路召回，再用 RRF 融合**

原来 BGE-M3 提供 dense + sparse 双路，reranker 收口；现在拆成：

| 路 | 实现 | 作用 |
|---|---|---|
| dense | DashScope `text-embedding-v4`，召回 20–30 条 | 语义泛化（“报销要几天” ↔ “费用核销时限”） |
| lexical | 本地内存 BM25，中文按 **字符二元组** 切词（不引 jieba），500–700 chunk 下 <10ms | 专有名词、制度名、编号精确命中 |

融合用 **RRF（Reciprocal Rank Fusion）** 而不是分数加权：

```
score(doc) = Σ_lane 1 / (60 + rank_lane(doc))
```

原因：cosine 与 BM25 的量纲不可比，加权融合需要每次标定归一化参数；RRF 只看名次，换模型/换语料都不用重调。这是去掉 reranker 后最省心、最稳的排法。

**③ 融合后加确定性的业务加权**（不引入模型）

- `dept` 命中意图路由判定的部门：+1 档；
- `how_to`（“怎么/如何”）问题优先「操作细则」类文档，普通问答优先「常见问答」；
- 同一 `source` 最多保留 2 块；相邻块（`chunk_index` 相差 1）同时命中时**合并上下文**（small-to-big），避免答案被切断；
- 最后取 top 3 给 LLM。

**④ 拒答与兜底**

- top1 cosine 低于 `KBQA_MIN_SCORE`（新增，默认关闭，标定后开启）→ 走 miss，不拼凑；
- `how_to` 场景 RAG miss 时回落 L1 速查卡（现有 `l1_fallback` 逻辑保留），并显式标注“未找到完整流程”；
- 只有在「top1 与 top3 分数几乎相同（margin < 0.02）」时，才考虑用一次轻量 LLM listwise 重排 3 条候选（约 0.5–1s）；**不做每问必排**，否则等于把 reranker 的延迟换个形式请回来。

**代价**：新增约 100 行 BM25 + 30 行 RRF，无需新依赖；查询侧多一次本地计算（<10ms），省掉 reranker 的 200–600ms。

**验收方式**：从 `role_qa_cases.yaml` + 制度语料构造 30–50 条问答对，对比改造前后 `Recall@3` / 无命中率 / 答非所问率；不要凭个例判断。

| 分支 | 角色 | 谁写 | 服务器行为 |
|---|---|---|---|
| `main` | 唯一开发/集成分支，完整前后端 + 数据 + 脚本 | 开发者（PR 合入） | 不直接部署 |
| `backend` | 发布产物：只含后端可运行单元 | 脚本/CI 从 main 生成 | 广州 `git clone -b backend` |
| `frontend` | 发布产物：只含静态前端 + Nginx 配置 | 脚本/CI 从 main 生成 | 香港 `git clone -b frontend` |

**核心纪律**

1. **只改 main，不改发布分支**。`backend` / `frontend` 是「构建产物」，由脚本强制重建并 force-push；任何直接提交都会在下次发布时被覆盖。
2. 发布分支**不追求保留历史**：采用 orphan 分支（每次一个提交），体积小、内容可完全复现；服务器更新一律 `git reset --hard origin/<branch>`，不要 `git pull`。
3. 两条分支使用**同一个发布标签**（如 `2026.10.24-1`），并各自写入 `BUILD_INFO` 文件；后端 `/api/v2/health` 回显、前端页脚展示，排查时能确认前后端是否同一版本。
4. 种子数据在 `backend/data/`：`knowledge/`、`kbqa_corpus/`、`case_seed.json`、`*.sql`。**`*.db` 与 `data/chroma*/` 不入库**——它们由首次启动生成并落在 Docker volume。
5. 私库访问用**部署公钥**（每台服务器一把只读 key），不要把 PAT 写进 compose 或 `.env`。

**`scripts/publish_branches.sh`（main 分支内，示意）**

```bash
#!/usr/bin/env bash
set -euo pipefail
TAG=${1:-$(date +%Y.%m.%d-%H%M)}
REPO=git@github.com:Hulk-Zhao/mfg-agent.git
ROOT=$(git rev-parse --show-toplevel)
WORK=$(mktemp -d)

# 先在临时目录组装「分支内容」，再一次性 commit，避免先推后补
stage_backend() {
  cp -r "$ROOT/backend/." "$WORK/backend/"
  mkdir -p "$WORK/backend/data"
  cp -r "$ROOT/data/knowledge" "$ROOT/data/kbqa_corpus" \
        "$ROOT/data/case_seed.json" "$ROOT/data/init.sql" \
        "$ROOT/data/seed_v3.sql" "$WORK/backend/data/"
}

stage_frontend() {
  cp -r "$ROOT/frontend/." "$WORK/frontend/"
}

publish() {                                   # $1=branch
  git worktree add --detach "$WORK/tree-$1" main
  cd "$WORK/tree-$1"
  git checkout --orphan "$1"
  git rm -rf . >/dev/null 2>&1 || true
  find . -mindepth 1 -maxdepth 1 ! -name .git -exec rm -rf {} +
  cp -r "$WORK/$1/." .
  echo "$TAG" > BUILD_INFO
  git add -A
  git commit -m "release($1): $TAG"
  git push -f "$REPO" "$1"
  cd - >/dev/null
  git worktree remove --force "$WORK/tree-$1"
}

stage_backend
stage_frontend
publish backend
publish frontend
rm -rf "$WORK"
```

> 分支内容完全由脚本组装：`backend` 分支 = `backend/` + 精选种子数据；`frontend` 分支 = `frontend/`。CI 版逻辑相同：`main` push 后由 GitHub Actions 执行脚本，并顺带构建镜像推 TCR。

**服务器侧更新（两条分支通用）**

```bash
cd /opt/mfg-agent
git fetch origin backend
git reset --hard origin/backend      # 发布分支无本地改动，reset 是安全且幂等的
docker compose up -d --build         # 或 pull + up -d（走 TCR 时）
```

`.env` 是 untracked 文件，`reset --hard` 不会覆盖它；务必确认 `.gitignore` 包含 `.env`、`data/*.db`、`data/chroma/`。

### 5.3 Docker 部署规范（两台均为 Docker CE）

两台机器都是「Docker CE」镜像（无预装业务环境），因此所有组件一律容器化，宿主机只保留 Docker 引擎 + compose 插件。以下规范两台通用。

**① 宿主机前置（一次性）**

```bash
# 确认版本：Compose 需 ≥ 2.20（本文使用 name/healthcheck 等 v2 语法）
docker version && docker compose version

# 若没有 compose 插件（部分 Docker CE 镜像只带 docker）：
apt-get update && apt-get install -y docker-compose-plugin

# 镜像加速（广州必备；香港可留空）
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"],
  "log-driver": "json-file",
  "log-opts": {"max-size": "20m", "max-file": "5"}
}
EOF
sudo systemctl restart docker
```

- 日志驱动统一在 daemon 层限流，避免 40GB 系统盘被容器日志写满；compose 里再写一遍是双保险。
- **不要**在宿主机安装 Python / Nginx / MySQL——镜像里全都有，宿主机安装只会让「哪份配置生效」变得不可查。

**② 镜像构建与分发**

| 方式 | 适用 | 做法 |
|---|---|---|
| A. 本机构建 + `docker save/load` | 首次上线、内网带宽好 | 本地 `docker build --platform linux/amd64`，`docker save \| gzip > app.tgz`，`scp` 到服务器 `docker load` |
| B. 腾讯云 TCR 个人版（推荐长期） | 频繁发版 | 本地 push，广州/香港 `docker compose pull`；CVM 走内网拉取更快 |
| C. 服务器直接 build | 应急改一行 | `docker compose build`，构建峰值约 1GB 内存，**必须在应用停止时做**，否则 4GB 机器有 OOM 风险 |

构建参数统一从 compose 传 `PIP_INDEX_URL`，不要在 Dockerfile 里写死某一个镜像源。

**③ 端口暴露的铁律**

Docker 的 `-p 8004:8004` 由 iptables 直接下发规则，**会绕过 ufw/firewalld**——在宿主机上 `ufw deny 8004` 是无效的。因此：

- 广州 8004 必须在**云控制台的防火墙/安全组**里限制来源，只放行香港 `43.132.214.124/32`；
- 香港 80/443 在云控制台放行全网；
- 上线后用外部机器验证：`curl --connect-timeout 3 http://129.204.108.45:8004/api/v2/health` 应当**超时**（而不是返回 JSON 后再去查日志）。

**④ 数据与卷**

- 所有可变数据只落在 named volume（`mfg_data`）或明确的 bind mount；**不要**把数据库文件放在镜像层。
- 容器内路径固定：`/app/data`（SQLite + Chroma）。升级镜像不触碰卷。
- 备份/恢复命令见 §7.5。
- `restart: unless-stopped` + `stop_grace_period: 30s`：避免正在写 SQLite 时被 SIGKILL。

**⑤ 时区与编码**

每个容器显式 `TZ=Asia/Shanghai`、`LANG=C.UTF-8`；否则日志时间、报告日期会与业务口径错位。

### 5.4 香港：Nginx

`frontend/nginx/default.conf`：

```nginx
upstream gz_backend {
    server 129.204.108.45:8004;
    keepalive 32;
}

server {
    listen 80;
    server_name hulkai.cn www.hulkai.cn;

    # Let's Encrypt webroot 校验：必须在 301 之前命中
    location /.well-known/acme-challenge/ {
        root /var/www/certbot;
    }

    location / {
        return 301 https://$host$request_uri;
    }
}

server {
    listen 443 ssl;
    http2 on;
    server_name hulkai.cn www.hulkai.cn;

    ssl_certificate     /etc/letsencrypt/live/hulkai.cn/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/hulkai.cn/privkey.pem;

    root  /usr/share/nginx/html;
    index index.html;
    client_max_body_size 20m;

    gzip on;
    gzip_types text/css application/javascript application/json image/svg+xml;
    gzip_min_length 1024;

    location / {
        try_files $uri $uri/ /index.html;
        add_header Cache-Control "no-cache";
    }

    # 带 ?v= 的静态资源长缓存；其余回源校验
    location ~* \.(js|css|svg|png|jpg|webp|woff2)$ {
        expires 30d;
        add_header Cache-Control "public, max-age=2592000";
    }

    location /api/ {
        proxy_pass http://gz_backend;
        proxy_http_version 1.1;
        proxy_set_header Host              $host;
        proxy_set_header X-Real-IP         $remote_addr;
        proxy_set_header X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_set_header Connection        "";

        # SSE 关键三项
        proxy_buffering off;
        proxy_cache off;
        chunked_transfer_encoding on;

        # 问数 90s / 事件流 90s，留足余量
        proxy_connect_timeout 10s;
        proxy_send_timeout    300s;
        proxy_read_timeout    300s;
    }
}
```

注意：

- `EventSource` 无法带 Authorization 头；事件流端点若要求令牌，需改成查询参数（现状演示模式不强制，保持即可）。
- DNS：`hulkai.cn` 与 `www.hulkai.cn` 的 A 记录指向香港 `43.132.214.124`；**不要**解析到广州（大陆节点对外提供 Web 需要 ICP 备案，且香港反代也失去意义）。
- 证书：香港服务器无需 ICP 备案，用 Let's Encrypt 签发即可（`.cn` 域名需完成实名认证，与备案是两件事）。申请时需 80/443 开放且 DNS 已生效；Nginx 容器挂载 `/etc/letsencrypt`。
- 若暂时无法签发证书，可先用 `https://43.132.214.124` 自签证书过渡（浏览器告警），但 `hulkai.cn` 的正式对外演示建议直接上正式证书。
- 香港 2C2G 只跑 Nginx，内存占用 < 100MB；开 `worker_processes 2`、`worker_connections 2048` 足够。

`frontend` 分支根目录的 `docker-compose.yml`：

```yaml
name: mfg-frontend

services:
  nginx:
    image: nginx:1.27-alpine
    container_name: mfg_nginx
    ports: ["80:80", "443:443"]
    environment:
      TZ: Asia/Shanghai
    volumes:
      - ./public:/usr/share/nginx/html:ro
      - ./nginx/default.conf:/etc/nginx/conf.d/default.conf:ro
      - letsencrypt:/etc/letsencrypt:ro
      - certbot_www:/var/www/certbot:ro
    restart: unless-stopped
    stop_grace_period: 10s
    healthcheck:
      test: ["CMD", "wget", "-q", "--spider", "http://localhost/"]
      interval: 30s
      timeout: 5s
      retries: 3
    logging:
      driver: json-file
      options: { max-size: "20m", max-file: "5" }

  certbot:
    image: certbot/certbot:latest
    container_name: mfg_certbot
    volumes:
      - letsencrypt:/etc/letsencrypt
      - certbot_www:/var/www/certbot
    entrypoint: >
      /bin/sh -c 'trap exit TERM;
      while :; do certbot renew --webroot -w /var/www/certbot --quiet;
      sleep 12h & wait $${!}; done'
    restart: unless-stopped

volumes:
  letsencrypt:
    name: mfg_letsencrypt
  certbot_www:
    name: mfg_certbot_www
```

**首次签发证书顺序**（Nginx 必须先起来，否则 webroot 校验拿不到文件）：

```bash
# 1) 先用 HTTP-only 配置启动（把 443 server 临时注释掉，或先只放 80）
docker compose up -d nginx

# 2) 申请证书（两个域名一起签）
docker compose run --rm certbot certonly --webroot -w /var/www/certbot \
  -d hulkai.cn -d www.hulkai.cn --email you@example.com --agree-tos -n

# 3) 启用 443 server 后重载
docker compose exec nginx nginx -s reload
```

续期：certbot 容器每 12h 自动 `renew`；证书更新后 Nginx 不会自动读取，需在宿主机加一条 cron：

```bash
# 每周一 03:20 重载（无证书变化时 reload 也是幂等的）
20 3 * * 1 docker compose -f /opt/mfg-agent/docker-compose.yml exec nginx nginx -s reload
```

> 静态文件用 bind mount（`./public`）而不是打进镜像：前端只有 2MB，更新只需 `git reset --hard` + reload，不必重建镜像；同时保证「git 拉下来的就是线上跑的」。

对应的 `backend/Dockerfile`（裁剪版，去掉本地模型后约 1.2–1.5GB）：

```dockerfile
FROM python:3.12-slim-bookworm

ARG PIP_INDEX_URL=https://mirrors.tencent.com/pypi/simple
ENV PYTHONUNBUFFERED=1 PYTHONDONTWRITEBYTECODE=1 \
    PIP_NO_CACHE_DIR=1 PIP_INDEX_URL=${PIP_INDEX_URL} \
    PYTHONPATH=/app/src TZ=Asia/Shanghai

WORKDIR /app
RUN apt-get update && apt-get install -y --no-install-recommends curl \
    && rm -rf /var/lib/apt/lists/*

# 依赖与代码分开拷贝，改代码不重装依赖
COPY pyproject.toml README.md ./
COPY src ./src
RUN pip install --no-cache-dir --timeout 120 --retries 3 .

COPY data/init.sql data/seed_v3.sql ./data/
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh && mkdir -p /app/data /app/logs

EXPOSE 8004
HEALTHCHECK --interval=30s --timeout=10s --start-period=90s --retries=3 \
  CMD curl -fsS http://localhost:8004/api/v2/health || exit 1
ENTRYPOINT ["/entrypoint.sh"]
```

> 关键差异：`pyproject.toml` 中删除 `torch / sentence-transformers / flagembedding / milvus-model / pymilvus / streamlit`，也不再 `COPY models`。否则镜像会多出约 6GB，4GB 内存的广州机器跑不动。

- **uvicorn 必须单 worker**：Chroma `PersistentClient` 以文件锁方式独占目录，多 worker 会互相踩踏。
- 不跑 MySQL / Milvus；Redis 可选（不配 `REDIS_URL` 会自动降级为无缓存，业务不受影响）。
- 建议加 2GB swap 兜底；Docker 日志限流，避免 40GB 盘被日志写满。
- 安全组入站：`8004` 仅允许 `43.132.214.124/32`；SSH 单独限源。

### 5.6 跨机链路安全

三种可选，按投入从低到高：

1. **安全组白名单 + HTTP**（最低成本，演示可用；跨境明文传输有合规风险）；
2. **广州侧自签 TLS + 香港 `proxy_ssl_verify off`**（加密，配置简单，推荐默认）；
3. **WireGuard 内网**（最稳，香港反代指向 `10.x.x.x`，无需暴露公网端口）。

### 5.7 前端需要的最小改动

- **API 基址**：无需改动（同源自动识别）。
- 建议新增一个可选覆盖：`window.__API_BASE__`（用于绕过香港直接连广州排障），不配置时行为不变。
- `/demo-story` 目录在当前仓库为空，若后续启用，需要把该目录一并复制到香港静态根。

```bash
curl -fsS localhost:8004/api/v2/health >/dev/null && echo OK

# 香港：重置 → 重载 Nginx（静态文件是 bind mount，无需重建镜像）
cd /opt/mfg-agent
git fetch origin frontend && git reset --hard origin/frontend
docker compose exec nginx nginx -s reload
```

回滚：把 `git reset --hard origin/backend` 换成上一个发布提交（发布分支每次只有一个提交，用 `git reflog` 或 TCR 镜像 tag 回退）：

```bash
# 方式一：镜像 tag 回退（推荐，发布时给镜像打同一标签）
IMAGE_TAG=mfg-agent-backend:2026.10.23-2 docker compose up -d

# 方式二：代码回退后重建
git reset --hard <上一个 release commit> && docker compose up -d --build
```

## 8. 资源与性能预算

| 项 | 广州 4C4G | 香港 2C2G |
|---|---|---|
| 常驻内存 | app 0.8–1.5GB + Chroma 0.1–0.3GB | Nginx 0.05–0.1GB |
| 峰值内存 | 问数并发 10 时约 2.2GB（不跑本地模型） | < 0.2GB |
| 磁盘 | 代码+依赖约 2GB，数据 < 1GB | 静态 2MB + 镜像 50MB |
| 启动时间 | 5–10s（不再加载 391MB/560MB 模型） | < 1s |

延迟变化（估算）：

- 本地 BGE-M3 编码：CPU 上单条 50–200ms；去掉后改为云端 **30–80ms**；
- 本地 Reranker：CPU 上 200–600ms；去掉后为 **0ms**，但召回数增加、DB 查询略增；
- 净效果：**单次问答预计快 200–500ms**，且启动内存下降 2GB 以上。

## 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 分数分布变化 | 拒答闸门失效，什么问都答 | 上线前重跑标定；阈值写入 YAML 并加注释 |
| 云端 API 限流/故障 | 检索不可用 | 重试+熔断+查询缓存；健康检查显式 `degraded`，不降级到编造 |
| 跨境链路延迟/抖动 | 页面加载慢 | 香港反代 keepalive + HTTP/2 + gzip；静态长缓存；接口合并现状已较好 |
| SSE 被缓冲 | 事件流假死 | Nginx 关闭 `proxy_buffering`，超时 300s |
| Chroma 单进程锁 | 多 worker 数据损坏 | `uvicorn --workers 1`；未来扩容改 Chroma Server/Qdrant |
| 香港单点 | 前端不可用 | 2C2G 极简，重启快；可加 Cloudflare 或备用域名 |
| 数据合规 | 文本出境/出司 | 案例入库前已脱敏；制度语料确认可送云端；必要时申请百炼私有化/专有实例 |
| 无 ICP 备案 | 大陆域名指向广州会被拦截 | 域名只解析到香港；广州仅做 IP 白名单反代，不对外提供 Web |

## 11. 备选方案（不推荐但可选）

1. **向量库上云**：阿里云 DashVector（与 DashScope 同生态，免运维、零本地内存）。代价：新增适配器、每查询多一跳网络、按量计费。数据量 < 2k 时收益不大。
2. **保留 Milvus**：需要至少 8GB 内存的广州机器；当前 4GB 会 OOM，不建议。
3. **保留本地 embedding 但换小模型**：如 `bge-small-zh`（约 100MB），CPU 可跑；但用户明确要求云端 embedding，且 4C 机器上仍不如 API 稳定。

## 13. 需要确认的三件事

1. **数据集归属**：方案默认「RAG 语料 / 业务库 / 向量索引全部放广州，香港只放静态前端」。若你希望香港也存一份原始语料（只读备份），需要额外同步机制。
2. **GitHub 仓库可见性与认证**：`mfg-agent` 若为私有库，需为两台服务器各配一把**只读部署公钥**；发布分支由脚本 force-push，建议在仓库设置里保护 `main` 并限制谁能推送发布分支。
3. **演示 vs 生产开关**：`CASE_DEMO_MODE` / 自动审批演示是否保留开启；若对外正式使用，建议关闭并接入真实审批。
