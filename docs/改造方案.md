## 1. 现状与目标

### 1.1 起点（v1 的问题）

v1 为了「静态与 API 分离」，长期维持一台香港 2C2G 只跑 Nginx，静态资源每次改稿都要
`git pull` 到香港机；跨境链路抖动会直接影响首屏；同时广州机的业务端口只能通过安全组
白名单暴露给香港 IP，排障与扩容都被这台小机器卡住。

### 1.2 本轮目标

1. **静态资源全部交给 COS + CDN**：不再依赖香港机器，不再占广州机 5Mbps 出口。
2. **广州机收敛为「API 网关 + 三个后端」**：只剩 80/443 对外，端口全部绑回环。
3. **发布链路标准化**：镜像由 CI 构建推 GHCR，服务器只 `login → pull → up`，
   4C4G 不再承担编译，也不再有「两台机器版本不一致」。
4. **接口路径与前端调用方式不变**：`/api/*`、`/hogo/api/*`、`/aps/*` 与 WebSocket
   路径保持原样，只把「从哪个域名访问」改成 `api.hulkai.cn`。

### 1.3 不变的部分（v1 已落地、v2 继续沿用）

- **Embedding 上云**：不再部署本地 BGE-M3，改用云端 Embedding 接口，维度 **1024**，
  单批 10 条、带重试与本地缓存（具体键见 `deploy/gz-api/.env.example` 的
  `EMBEDDING_*` / `DASHSCOPE_*` 段）。换模型必须全量重建索引，向量空间不兼容。
- **去掉本地 Reranker**：改为「扩召回 + 确定性重排 + 云端重排（可选）」，
  召回阈值是按新模型分数分布重新标定的，不要沿用旧阈值。
- **向量库**：Chroma 嵌入式持久化（约 1700–2000 chunk），不跑 Milvus。
- **中间件**：Redis 可选（compose 内置 256MB 上限）；不跑 MySQL。

## 2. 最终拓扑

```
                 浏览器 (HTTPS)
        ┌──────────────┴───────────────┐
        │ hulkai.cn / www.hulkai.cn    │        api.hulkai.cn
        ▼                              ▼
  腾讯云 CDN（COS 源）          广州轻量 129.204.108.45
  中国境内 / 网页小文件          4C4G · 60G · 5Mbps · 500GB/月
        │ 回源 HTTP                    │ 80/443  Nginx（容器）
        ▼ 回源 HOST=桶默认域名         ├─ /api/*      → mfg-api      :8004（FastAPI + SSE）
  COS 桶 hulkai-cdn-1301421942         ├─ /hogo/api/* → hogo-qa      :8788（Node）
  （ap-guangzhou，私有读写）           ├─ /aps/*      → aps-backend  :8080（Spring Boot + WS）
        │                              ├─ /healthz    → 200
        └─ /index.html 等静态文件       └─ /           → 302 回站点首页
                                             │
                          ┌──────────────────┴───────────────┐
                          ▼                                  ▼
                 GitHub Actions → GHCR              腾讯云模型服务（公网）
                 ghcr.io/<owner>/<repo>-*            Embedding / 对话 / 重排
```

要点：

1. **两条链路完全分开**：静态只走 CDN→COS，动态只走 `api.hulkai.cn`。API 不经 CDN，
   避免动态响应被缓存、也避免回源流量计费。
2. **广州机不再有静态目录**：容器内 Nginx 默认不提供任何静态文件；
   `/opt/hulkai/site` 与 CDN 回源 IP 段在现行形态下都不需要（灾备才用，见 8.3）。
3. **不同源带来 CORS**：`Origin` 来自 `https://hulkai.cn` / `https://www.hulkai.cn`，
   由 Nginx 统一注入，后端代码不改。
4. **SSE 与 WebSocket 仍在 API 域名下**：`/api/v2/events` 关闭缓冲；
   `/aps/ws/*` 保持 Upgrade 透传，读写超时 3600s。

## 3. 域名与路由分工

### 3.1 站点域名：`hulkai.cn` / `www.hulkai.cn` → CDN → COS

控制台已确认的配置（以控制台为准）：

| 项 | 值 |
| --- | --- |
| 加速域名 | `hulkai.cn`（加速区域中国境内、加速类型「网页小文件」） |
| 源站类型 | **COS 源** |
| 桶 / 地域 | `hulkai-cdn-1301421942` / `ap-guangzhou` |
| 回源协议 | **HTTP**（COS 静态网站不需要 HTTPS 回源） |
| 回源 HOST | 桶默认域名 `hulkai-cdn-1301421942.cos.ap-guangzhou.myqcloud.com` |
| 桶权限 | 私有读写 + CDN 私有桶访问授权（不要改成公有读） |
| CNAME | `hulkai.cn.cdn.dnsv1.com` |
| `www.hulkai.cn` | **加速域名尚未创建**，需按 9.1 补建同源配置 |

桶内布局与 URL 严格一一对应（发布脚本已按此组装）：

| 线上 URL | 桶内对象 | 来源 |
| --- | --- | --- |
| `https://hulkai.cn/` | `/index.html` 等 | `site/public/` |
| `/blog/`、`/demo/` | `/blog/`、`/demo/` | `site/public/blog`、`site/public/demo` |
| `/demo/mfg/` | `/demo/mfg/` | `projects/mfg-agent/web`（原生 JS，无需构建） |
| `/demo/hogo-qa/` | `/demo/hogo-qa/` | hogo 前端构建产物（history 路由） |
| `/demo/mfg-agent-platform/` | `/demo/mfg-agent-platform/` | APS 前端构建产物（history 路由） |

### 3.2 API 域名：`api.hulkai.cn` → 广州机 Nginx

`api.hulkai.cn` 为 A 记录直连 `129.204.108.45`，不经 CDN。容器内 Nginx 是唯一对外入口：

| 路径 | 上游 | 处理要点 |
| --- | --- | --- |
| `/api/*` | `app:8004` | 透传；`proxy_buffering off`（SSE `/api/v2/events` 逐条下发）；读写 300s |
| `/hogo/api/*` | `hogo-qa:8788` | `rewrite ^/hogo/(.*)$ /$1` 去掉前缀 |
| `/aps/*` | `aps-backend:8080` | 去前缀；`Upgrade`/`Connection` 透传；读写 3600s（求解进度 WebSocket） |
| `/healthz` | 本机 | 200 `ok`，容器健康检查用 |
| 其它 | — | 302 到 `https://hulkai.cn`（API 子域不承载页面） |

实现位置：[api.conf.template](../deploy/gz-api/nginx/templates/api.conf.template)
（`/api/` 约 L92-113、`/hogo/api/` L117-132、`/aps/` L137-156）。

Nginx 同时负责：

- **CORS**：`map $http_origin` 只回显白名单（`SITE_ORIGIN_PRIMARY` / `SITE_ORIGIN_WWW`），
  不在名单里就不发 `Access-Control-Allow-Origin`；`OPTIONS` 直接 204，不进后端。
- **剥掉上游 CORS**：`proxy_hide_header` 处理 `Access-Control-*` 六个头，
  防止与网关的 `add_header` 叠加成重复头导致浏览器判失败。
- **对外暴露头**：`X-Template-Filename`、`X-Trace-Id` 等由 `Access-Control-Expose-Headers` 放行。
- **无 Cookie**：三套应用都是 `Authorization: Bearer` + `localStorage`，因此不发
  `Access-Control-Allow-Credentials`；将来若引入 Cookie，必须同步改 CORS 策略（见 README §11）。

### 3.3 为什么必须改三处前端

静态与 API 不同源后，「页面同源即后端」的假设失效，三个子应用各自换入口：

| 子应用 | 改造方式 | 落地文件 |
| --- | --- | --- |
| mfg 演示屏（原生 JS） | 页面加载 `config.js`，发布时写入 `window.MFG_API_BASE`；`app.js` 探测逻辑优先用它，命中即直连、不再做同源/本机候选竞速 | `projects/mfg-agent/web/config.js`、`app.js`、`index.html` |
| hogo-qa（React + Vite） | 构建期 `VITE_API_BASE` 覆盖认证前缀，未配置时保持原 `BASE_URL + api/` 行为 | `projects/hogo-qa/frontend/src/services/auth/authClient.ts` |
| 智能 APS（Vue3 + Vite） | 构建期注入绝对 REST 与 `wss://` 地址，关闭 Mock | 构建参数，源码无需改（`http.ts`、`solve.ts` 已支持） |

具体注入值见 4.2；三处都遵循同一条原则：**源码默认行为不变，部署期由构建/发布注入**。

## 4. 前端构建与静态发布

### 4.1 一条命令

`deploy/cos/publish.ps1`（本地 Windows 执行，仓库根目录）：

```
构建 hogo → 构建 APS → 复制 site/public 与 mfg 前端 → 写 demo/mfg/config.js → coscli sync
```

默认桶 `hulkai-cdn-1301421942`、地域 `ap-guangzhou`（可被 `-Bucket` / `-Region` 覆盖），
`-SkipBuild` 只重传、`-SkipUpload` 只产 `deploy/cos/dist/`（灾备用）、`-Delete` 清理多余对象
（首次上线不要加）。脚本不读也不写任何密钥，coscli 凭据在本机 `~/.cos.yaml`。

### 4.2 构建期注入的地址

| 子应用 | 变量 | 值 |
| --- | --- | --- |
| hogo | `HOGO_BASE` | `/demo/hogo-qa/` |
| hogo | `VITE_API_BASE` | `https://api.hulkai.cn/hogo/api/` |
| APS | `APS_BASE` | `/demo/mfg-agent-platform/` |
| APS | `VITE_API_BASE_URL` | `https://api.hulkai.cn/aps/api/v1` |
| APS | `VITE_WS_BASE_URL` | `wss://api.hulkai.cn/aps` |
| APS | `VITE_ENABLE_MOCK` | `false` |
| mfg | `window.MFG_API_BASE` | `https://api.hulkai.cn`（运行时写入 `config.js`） |

### 4.3 缓存与 SPA 回退

- HTML 与 `config.js` 不长缓存（每次发布要能立刻生效）；带 hash 的 `assets/` 长缓存；
  其余静态资源走默认 30 天。规则配在 CDN 控制台，不在仓库里。
- 两个 history 路由子应用（hogo、APS）需要「未知路径回 index.html」，
  但 **COS 静态网站只有一个全局错误文档**，两个子应用的回退目标不同。现行做法：
  COS 全局错误文档设为 `index.html`，CDN 侧只对 `/demo/hogo-qa/` 与
  `/demo/mfg-agent-platform/` 两个前缀做回退重写；**禁止**把「404 → 首页」配成全局规则。
- 代码里用 `?v=` 版本号破缓存（本轮把 `home.css?v=` 统一提到 `20261111a`）。

## 5. 镜像构建与发布链路

### 5.1 CI → GHCR

- 工作流：`.github/workflows/build-images.yml`；触发 `push main` 与手动 `workflow_dispatch`。
- 权限：`contents: read` + `packages: write`；用自动注入的 `GITHUB_TOKEN`，**不需要额外 secret**。
- 产物（`<owner>/<repo>` 全小写）：

| 服务 | 镜像 |
| --- | --- |
| mfg-agent FastAPI | `ghcr.io/<owner>/<repo>-mfg-api:sha-<7>` |
| 智能 APS | `ghcr.io/<owner>/<repo>-aps-backend:sha-<7>` |
| Hogo-QA | `ghcr.io/<owner>/<repo>-hogo-qa:sha-<7>` |

- 同时推 `latest`，但**生产只用 `sha-*`**，三个镜像共用同一个 tag，便于整体回滚。
- Actions Summary 会打印三个镜像名与 `REGISTRY` / `IMAGE_TAG` 两行，直接抄进服务器 `.env`。

### 5.2 服务器只 pull

`deploy/gz-api/docker-compose.yml` 里每个后端都是：
`image: ${REGISTRY}/<服务>${IMAGE_TAG}` + 保留的 `build:` 兜底段。因此服务器必须
`docker compose pull` 后 `up -d --no-build`；不加 `--no-build` 时若镜像缺失会尝试本地编译。

| 服务 | 镜像来源 | 内存上限 |
| --- | --- | --- |
| `app`（mfg-api） | GHCR | 2800m（memswap 3400m） |
| `aps-backend` | GHCR | 700m（memswap 900m） |
| `aps-postgres` | `postgres:15` 公共镜像 | 256m |
| `redis` | `redis:7-alpine`，`maxmemory 256mb`、关闭 RDB 落盘 | — |
| `hogo-qa` | GHCR | 160m |
| `nginx` | `nginx:1.27-alpine` | — |

本地 build 只作 CI 不可用时的兜底（峰值内存：mfg 约 1.0–1.5G、APS 约 2.5–3.0G、
hogo 约 0.8–1.0G），4C4G 上必须加 swap 且 `COMPOSE_PARALLEL_LIMIT=1`。

## 6. 配置与密钥的放置约定

| 内容 | 放哪 | 入库 | 说明 |
| --- | --- | --- | --- |
| 环境变量键清单 | `deploy/gz-api/.env.example` | 是 | 只有键名、默认值与占位，无真实值 |
| 真实环境变量 | `deploy/gz-api/.env` | **否**（已被 `.gitignore` 覆盖） | 服务器本地 `chmod 600`；`AUTH_SECRET`、`APS_SECURITY_JWT_SECRET` 用 `openssl rand -hex 32` 生成 |
| TLS 证书 | `deploy/gz-api/certs/`（api 必需；`hulkai.cn` 仅灾备） | **否** | 文件名必须等于 `API_DOMAIN` / `SITE_DOMAIN`，私钥 `chmod 600` |
| GHCR 读凭据 | 服务器 shell 环境或凭据管理器 | 否 | PAT 只勾 `read:packages`；包设为 Public 时可不登录 |
| COS 凭据 | 本机 `~/.cos.yaml`（`coscli config add`） | 否 | 不写进脚本、`.env.example`、CI |
| 业务密钥（模型 API Key、DB 口令、演示口令） | 只在 `.env` | 否 | 前端产物、镜像、CI 日志里一律不得出现 |
| GitHub 仓库配置 | 无需 Secrets；可选 Variables `PIP_INDEX_URL`、`APS_MAVEN_MIRROR_URL` | — | 缺省已内置腾讯云 pip / 阿里云 Maven 镜像 |

约定：**仓库里永远只有占位**。任何需要真值的地方，都在服务器 `.env` 或本机凭据里补齐。

## 8. 回滚

| 场景 | 做法 | 代价 |
| --- | --- | --- |
| 后端版本异常 | `.env` 里把 `IMAGE_TAG` 改回上一个可用的 `sha-*` → `pull` → `up -d --no-build` | 分钟级，仅后端 |
| 静态站内容异常 | 重新跑上一版 `publish.ps1`（或 `-SkipBuild` 用旧产物）覆盖桶 + 刷新 CDN | 分钟级，仅静态 |
| COS/CDN 故障 | 灾备：服务器 `SERVE_STATIC_ORIGIN=1` + 放 `hulkai.cn` 证书 + 同步静态到 `/opt/hulkai/site` + 填 CDN 回源 IP 段 → CDN 改回「自有源」；恢复后改回 `0` | 占用 5Mbps 出口，只宜临时兜底 |
| 整体退回 v1 | 启用 `deploy/hk-web/` 旧配置（已标注退役，仅作参考） | 需要香港机器与旧证书，不推荐 |

灾备形态存在的意义只有一个：**COS 或 CDN 短期不可用时，站点还能从广州机吐出来**。
默认必须是关闭状态，否则 5Mbps 会被静态流量吃满、拖垮 API。

## 9. 控制台侧仍需人工完成

这些都不在仓库里，代码改完也不会自动生效：

1. **`www.hulkai.cn` 加速域名**：复制 `hulkai.cn` 的源站配置新建，绑定同一张证书，
   DNS 加 `www` 的 CNAME（同 `hulkai.cn.cdn.dnsv1.com`）。未建之前，`www` 访问不通。
2. **证书**：CDN 侧上传 `*.hulkai.cn`（或分别绑定 `hulkai.cn` / `www.hulkai.cn`）；
   服务器侧放 `certs/api.hulkai.cn.pem|key`，灾备时再加 `hulkai.cn.pem|key`。
3. **缓存规则**：HTML 与 `config.js` 不长缓存、`assets/` 长缓存、其余默认；
   发布后刷新对应目录。

#### 3. 关键改造一：Embedding 上云（DashScope）

##### 3.1 选型

- 模型：`text-embedding-v4`，维度取 **1024**（v4 支持 2048/1536/1024/768/512/256/128/64；1024 与现有 schema 一致，检索质量与成本平衡）。
- 接口：OpenAI 兼容模式 `https://dashscope.aliyuncs.com/compatible-mode/v1/embeddings`（广州访问国内域名，延迟约 20–50ms）。
- 调用约束（以实现时官方文档为准）：
  - 单次请求最多 **10 条文本**；
  - 单条文本上限 8192 token；
  - 有 RPM/TPM 限额，需要重试与并发上限。
- **必须全量重建索引**：哈希/ONNX/BGE 向量空间与新模型不兼容；即使维度同为 1024 也不能混用。

##### 3.2 新增模块 `common/embedding.py`

职责：唯一的 embedding 出口（业务代码不直接调 SDK）。

```python
class CloudEmbedder:
    def encode(self, texts: list[str]) -> list[list[float]]: ...   # 自动分批(≤10)+重试+LRU
    def encode_one(self, text: str) -> list[float]: ...
    def health(self) -> tuple[bool, str]: ...                       # 带 TTL 的小样本探针

def get_embedder() -> CloudEmbedder: ...                            # 进程级单例
```

实现要点：

| 项 | 做法 |
|---|---|
| 分批 | `batch_size=10`（env 可调，硬上限 10） |
| 重试 | 指数退避 3 次，仅对 429/5xx/超时；4xx 立即失败 |
| 超时 | 单请求 15s；整体索引任务按批累计日志 |
| 缓存 | 查询侧 LRU（默认 2048 条），键为模型名+文本 hash；索引侧不缓存 |
| 失败语义 | **fail-closed**：索引任务失败→报错退出；查询失败→上层返回 `degraded`，不编造结果 |
| 可靠性 | 连续失败 5 次熔断 30s，健康检查显示 `down` |

#### 4. 关键改造二：去掉 Reranker

##### 4.1 现状判断

- KBQA 链路（`search_kb`）目前依赖 BGE-Reranker 提升 top-k 精度；
- 案例域**本来就是确定性重排**（状态权重 × 新鲜度 × 有效性），并没有用神经网络重排；
- 因此「去 reranker」的实际工作只有两处：`rag_tools` 删代码、案例域调候选数与阈值。

##### 4.2 替代策略（不引入任何本地模型）

| 环节 | 替代做法 |
|---|---|
| 召回 | 候选数从 12 提到 **18–24**（`n_results` 的 4–6 倍），保证答案在候选池里 |
| 精排 | 复用现有确定性重排：`status_weight × freshness × verified` + 受控术语命中加成 |
| 拒答 | 用 **cosine 相似度绝对值 + 术语闸门**；重新标定 `case_policy.yaml` 三个阈值 |
| KBQA | 增加可选 `KBQA_MIN_SCORE`（默认关闭），低于阈值走「检索不到」而不是让 LLM 自由发挥 |

##### 4.3 必做：阈值重标定

`case_policy.yaml` 明确写了「换真实 embedding 后必须重跑标定」，且当前值（0.18/0.20/0.27）是按哈希分数定的。云端 embedding 的无关问句相似度通常在 0.3–0.5，**直接沿用的结果是「什么都答」**。

做法：

1. 用 `data/case_seed.json` + 20 条无关问题（食堂、天气、股票…）构造标定集；
2. 跑现有 `tools/calibrate_answer_thresholds.py`（或按其逻辑改为调用新 embedder）；
3. 取「无关组 p95」与「相关组最低分」之间的间隔，设置 `answer_min_score` / `low_confidence_threshold` / `answer_score_without_terms`；
4. 把新值与语料规模一起写回 YAML 注释，避免下次又被当成恒定真理。

**标定在哪跑**：不必在服务器上跑。标定只依赖「同一个 embedding 模型 + 同一份案例语料」，与部署位置无关。推荐本地（开发机）跑：

- 条件：`EMBEDDING_MODEL=text-embedding-v4`、`EMBEDDING_DIM=1024` 与生产完全一致；使用 `data/case_seed.json` 同一份语料；配同一个 DashScope key。
- 产出：三个阈值写回 `case_policy.yaml`，随代码部署到广州即可。
- 不建议用 `CASE_VECTOR_BACKEND=memory` 做标定——哈希分数的分布与云端 cosine 完全不同，标出来的值没有意义；标定必须走云端 embedding + cosine。
- 服务器上只在验收阶段复跑一次「抽样对照」（10 条问题看分数区间），确认部署环境与本地一致即可。

##### 4.4 制度库（KBQA）排序方案（同样去 Reranker）

制度问答的检索链路比案例域更依赖 reranker，因为语料是 16 个部门、内容高度相似的制度条文。去掉 reranker 后**不能只靠单一 dense 相似度**，建议按下面四层排：

**① 先分级，别让所有问题都进向量检索**（现有架构已具备，保持不变）

```
L0 缓存 → L1 FAQ 精确匹配（纯词面，无 embedding）
        → L1.5 域内意图（kbqa_intent 词表，sub-ms）
        → L2 向量检索（只处理长尾）
```

大量高频问题在 L1 就被拦掉，L2 只承担长尾——这本身就把对精排的依赖降了一半。

**② L2 用「dense + 本地 BM25」两路召回，再用 RRF 融合**

原来 BGE-M3 提供 dense + sparse 双路，reranker 收口；现在拆成：

| 路 | 实现 | 作用 |
|---|---|---|
| dense | DashScope `text-embedding-v4`，召回 20–30 条 | 语义泛化（“报销要几天” ↔ “费用核销时限”） |
| lexical | 本地内存 BM25，中文按 **字符二元组** 切词（不引 jieba），500–700 chunk 下 <10ms | 专有名词、制度名、编号精确命中 |

融合用 **RRF（Reciprocal Rank Fusion）** 而不是分数加权：

```
score(doc) = Σ_lane 1 / (60 + rank_lane(doc))
```

原因：cosine 与 BM25 的量纲不可比，加权融合需要每次标定归一化参数；RRF 只看名次，换模型/换语料都不用重调。这是去掉 reranker 后最省心、最稳的排法。

**③ 融合后加确定性的业务加权**（不引入模型）

- `dept` 命中意图路由判定的部门：+1 档；
- `how_to`（“怎么/如何”）问题优先「操作细则」类文档，普通问答优先「常见问答」；
- 同一 `source` 最多保留 2 块；相邻块（`chunk_index` 相差 1）同时命中时**合并上下文**（small-to-big），避免答案被切断；
- 最后取 top 3 给 LLM。

**④ 拒答与兜底**

- top1 cosine 低于 `KBQA_MIN_SCORE`（新增，默认关闭，标定后开启）→ 走 miss，不拼凑；
- `how_to` 场景 RAG miss 时回落 L1 速查卡（现有 `l1_fallback` 逻辑保留），并显式标注“未找到完整流程”；
- 只有在「top1 与 top3 分数几乎相同（margin < 0.02）」时，才考虑用一次轻量 LLM listwise 重排 3 条候选（约 0.5–1s）；**不做每问必排**，否则等于把 reranker 的延迟换个形式请回来。

**代价**：新增约 100 行 BM25 + 30 行 RRF，无需新依赖；查询侧多一次本地计算（<10ms），省掉 reranker 的 200–600ms。

**验收方式**：从 `role_qa_cases.yaml` + 制度语料构造 30–50 条问答对，对比改造前后 `Recall@3` / 无命中率 / 答非所问率；不要凭个例判断。

##### 5.2 Git 仓库与双分支发布

仓库：`https://github.com/Hulk-Zhao/mfg-agent.git`

| 分支 | 角色 | 谁写 | 服务器行为 |
|---|---|---|---|
| `main` | 唯一开发/集成分支，完整前后端 + 数据 + 脚本 | 开发者（PR 合入） | 不直接部署 |
| `backend` | 发布产物：只含后端可运行单元 | 脚本/CI 从 main 生成 | 广州 `git clone -b backend` |
| `frontend` | 发布产物：只含静态前端 + Nginx 配置 | 脚本/CI 从 main 生成 | 香港 `git clone -b frontend` |

**核心纪律**

1. **只改 main，不改发布分支**。`backend` / `frontend` 是「构建产物」，由脚本强制重建并 force-push；任何直接提交都会在下次发布时被覆盖。
2. 发布分支**不追求保留历史**：采用 orphan 分支（每次一个提交），体积小、内容可完全复现；服务器更新一律 `git reset --hard origin/<branch>`，不要 `git pull`。
3. 两条分支使用**同一个发布标签**（如 `2026.10.24-1`），并各自写入 `BUILD_INFO` 文件；后端 `/api/v2/health` 回显、前端页脚展示，排查时能确认前后端是否同一版本。
4. 种子数据在 `backend/data/`：`knowledge/`、`kbqa_corpus/`、`case_seed.json`、`*.sql`。**`*.db` 与 `data/chroma*/` 不入库**——它们由首次启动生成并落在 Docker volume。
5. 私库访问用**部署公钥**（每台服务器一把只读 key），不要把 PAT 写进 compose 或 `.env`。

**`scripts/publish_branches.sh`（main 分支内，示意）**

```bash
#!/usr/bin/env bash
set -euo pipefail
TAG=${1:-$(date +%Y.%m.%d-%H%M)}
REPO=git@github.com:Hulk-Zhao/mfg-agent.git
ROOT=$(git rev-parse --show-toplevel)
WORK=$(mktemp -d)

# 先在临时目录组装「分支内容」，再一次性 commit，避免先推后补
stage_backend() {
  cp -r "$ROOT/backend/." "$WORK/backend/"
  mkdir -p "$WORK/backend/data"
  cp -r "$ROOT/data/knowledge" "$ROOT/data/kbqa_corpus" \
        "$ROOT/data/case_seed.json" "$ROOT/data/init.sql" \
        "$ROOT/data/seed_v3.sql" "$WORK/backend/data/"
}

stage_frontend() {
  cp -r "$ROOT/frontend/." "$WORK/frontend/"
}

publish() {                                   # $1=branch
  git worktree add --detach "$WORK/tree-$1" main
  cd "$WORK/tree-$1"
  git checkout --orphan "$1"
  git rm -rf . >/dev/null 2>&1 || true
  find . -mindepth 1 -maxdepth 1 ! -name .git -exec rm -rf {} +
  cp -r "$WORK/$1/." .
  echo "$TAG" > BUILD_INFO
  git add -A
  git commit -m "release($1): $TAG"
  git push -f "$REPO" "$1"
  cd - >/dev/null
  git worktree remove --force "$WORK/tree-$1"
}

stage_backend
stage_frontend
publish backend
publish frontend
rm -rf "$WORK"
```

> 分支内容完全由脚本组装：`backend` 分支 = `backend/` + 精选种子数据；`frontend` 分支 = `frontend/`。CI 版逻辑相同：`main` push 后由 GitHub Actions 执行脚本，并顺带构建镜像推 TCR。

**服务器侧更新（两条分支通用）**

```bash
cd /opt/mfg-agent
git fetch origin backend
git reset --hard origin/backend      # 发布分支无本地改动，reset 是安全且幂等的
docker compose up -d --build         # 或 pull + up -d（走 TCR 时）
```

`.env` 是 untracked 文件，`reset --hard` 不会覆盖它；务必确认 `.gitignore` 包含 `.env`、`data/*.db`、`data/chroma/`。

##### 5.3 Docker 部署规范（两台均为 Docker CE）

两台机器都是「Docker CE」镜像（无预装业务环境），因此所有组件一律容器化，宿主机只保留 Docker 引擎 + compose 插件。以下规范两台通用。

**① 宿主机前置（一次性）**

```bash
# 确认版本：Compose 需 ≥ 2.20（本文使用 name/healthcheck 等 v2 语法）
docker version && docker compose version

# 若没有 compose 插件（部分 Docker CE 镜像只带 docker）：
apt-get update && apt-get install -y docker-compose-plugin

# 镜像加速（广州必备；香港可留空）
sudo tee /etc/docker/daemon.json >/dev/null <<'EOF'
{
  "registry-mirrors": ["https://mirror.ccs.tencentyun.com"],
  "log-driver": "json-file",
  "log-opts": {"max-size": "20m", "max-file": "5"}
}
EOF
sudo systemctl restart docker
```

- 日志驱动统一在 daemon 层限流，避免 40GB 系统盘被容器日志写满；compose 里再写一遍是双保险。
- **不要**在宿主机安装 Python / Nginx / MySQL——镜像里全都有，宿主机安装只会让「哪份配置生效」变得不可查。

**② 镜像构建与分发**

| 方式 | 适用 | 做法 |
|---|---|---|
| A. 本机构建 + `docker save/load` | 首次上线、内网带宽好 | 本地 `docker build --platform linux/amd64`，`docker save \| gzip > app.tgz`，`scp` 到服务器 `docker load` |
| B. 腾讯云 TCR 个人版（推荐长期） | 频繁发版 | 本地 push，广州/香港 `docker compose pull`；CVM 走内网拉取更快 |
| C. 服务器直接 build | 应急改一行 | `docker compose build`，构建峰值约 1GB 内存，**必须在应用停止时做**，否则 4GB 机器有 OOM 风险 |

构建参数统一从 compose 传 `PIP_INDEX_URL`，不要在 Dockerfile 里写死某一个镜像源。

**③ 端口暴露的铁律**

Docker 的 `-p 8004:8004` 由 iptables 直接下发规则，**会绕过 ufw/firewalld**——在宿主机上 `ufw deny 8004` 是无效的。因此：

- 广州 8004 必须在**云控制台的防火墙/安全组**里限制来源，只放行香港 `43.132.214.124/32`；
- 香港 80/443 在云控制台放行全网；
- 上线后用外部机器验证：`curl --connect-timeout 3 http://129.204.108.45:8004/api/v2/health` 应当**超时**（而不是返回 JSON 后再去查日志）。

**④ 数据与卷**

- 所有可变数据只落在 named volume（`mfg_data`）或明确的 bind mount；**不要**把数据库文件放在镜像层。
- 容器内路径固定：`/app/data`（SQLite + Chroma）。升级镜像不触碰卷。
- 备份/恢复命令见 §7.5。
- `restart: unless-stopped` + `stop_grace_period: 30s`：避免正在写 SQLite 时被 SIGKILL。

**⑤ 时区与编码**

每个容器显式 `TZ=Asia/Shanghai`、`LANG=C.UTF-8`；否则日志时间、报告日期会与业务口径错位。

##### 5.6 跨机链路安全

三种可选，按投入从低到高：

1. **安全组白名单 + HTTP**（最低成本，演示可用；跨境明文传输有合规风险）；
2. **广州侧自签 TLS + 香港 `proxy_ssl_verify off`**（加密，配置简单，推荐默认）；
3. **WireGuard 内网**（最稳，香港反代指向 `10.x.x.x`，无需暴露公网端口）。

- **API 基址**：无需改动（同源自动识别）。
- 建议新增一个可选覆盖：`window.__API_BASE__`（用于绕过香港直接连广州排障），不配置时行为不变。

#### 8. 资源与性能预算

| 项 | 广州 4C4G | 香港 2C2G |
|---|---|---|
| 常驻内存 | app 0.8–1.5GB + Chroma 0.1–0.3GB | Nginx 0.05–0.1GB |
| 峰值内存 | 问数并发 10 时约 2.2GB（不跑本地模型） | < 0.2GB |
| 磁盘 | 代码+依赖约 2GB，数据 < 1GB | 静态 2MB + 镜像 50MB |
| 启动时间 | 5–10s（不再加载 391MB/560MB 模型） | < 1s |

延迟变化（估算）：

- 本地 BGE-M3 编码：CPU 上单条 50–200ms；去掉后改为云端 **30–80ms**；
- 本地 Reranker：CPU 上 200–600ms；去掉后为 **0ms**，但召回数增加、DB 查询略增；
- 净效果：**单次问答预计快 200–500ms**，且启动内存下降 2GB 以上。

#### 10. 风险与对策

| 风险 | 影响 | 对策 |
|---|---|---|
| 分数分布变化 | 拒答闸门失效，什么问都答 | 上线前重跑标定；阈值写入 YAML 并加注释 |
| 云端 API 限流/故障 | 检索不可用 | 重试+熔断+查询缓存；健康检查显式 `degraded`，不降级到编造 |
| 跨境链路延迟/抖动 | 页面加载慢 | 香港反代 keepalive + HTTP/2 + gzip；静态长缓存；接口合并现状已较好 |
| SSE 被缓冲 | 事件流假死 | Nginx 关闭 `proxy_buffering`，超时 300s |
| Chroma 单进程锁 | 多 worker 数据损坏 | `uvicorn --workers 1`；未来扩容改 Chroma Server/Qdrant |
| 香港单点 | 前端不可用 | 2C2G 极简，重启快；可加 Cloudflare 或备用域名 |
| 数据合规 | 文本出境/出司 | 案例入库前已脱敏；制度语料确认可送云端；必要时申请百炼私有化/专有实例 |
| 无 ICP 备案 | 大陆域名指向广州会被拦截 | 域名只解析到香港；广州仅做 IP 白名单反代，不对外提供 Web |

#### 11. 备选方案（不推荐但可选）

1. **向量库上云**：阿里云 DashVector（与 DashScope 同生态，免运维、零本地内存）。代价：新增适配器、每查询多一跳网络、按量计费。数据量 < 2k 时收益不大。
2. **保留 Milvus**：需要至少 8GB 内存的广州机器；当前 4GB 会 OOM，不建议。
3. **保留本地 embedding 但换小模型**：如 `bge-small-zh`（约 100MB），CPU 可跑；但用户明确要求云端 embedding，且 4C 机器上仍不如 API 稳定。

#### 13. 需要确认的三件事

1. **数据集归属**：方案默认「RAG 语料 / 业务库 / 向量索引全部放广州，香港只放静态前端」。若你希望香港也存一份原始语料（只读备份），需要额外同步机制。
2. **GitHub 仓库可见性与认证**：`mfg-agent` 若为私有库，需为两台服务器各配一把**只读部署公钥**；发布分支由脚本 force-push，建议在仓库设置里保护 `main` 并限制谁能推送发布分支。
3. **演示 vs 生产开关**：`CASE_DEMO_MODE` / 自动审批演示是否保留开启；若对外正式使用，建议关闭并接入真实审批。
